## **Reporting Period:** 2026-10-01 - 2026-10-26

**Overall Status:** On Track

### Project: Laptop S0i3 Support

#### Overall Goal

Get modern laptops (primarily AMD-based, such as the Framework) to reliably suspend to idle and reach the S0i3 deep sleep state on FreeBSD, and resume cleanly from it, so that laptops get battery life in suspend comparable to other operating systems.

#### Current Work

- **Suspend-to-idle loop:** Instead of suspending once and resuming on the first interrupt, the system needs to stay in a loop in suspend-to-idle, process events which don't need to wake the system (e.g. battery level events), and only fully resume on genuine wake events. This is the last major missing piece for suspend-to-idle support.
- **Fixing hangs during and after suspend:** Some events processed while suspended (such as plugging/unplugging AC) or after resume could lock up the system.
- **Suspending USB4 correctly:** USB4 controllers must be correctly suspended for the system to enter S0i3.
- **Debugging tools:** Hangs/crashes during suspend-to-idle are hard to debug, as the machine is effectively unresponsive. Better tooling makes it much easier to narrow down issues, especially on new hardware.
- **Testing on other hardware:** Bringing up S0i3 entry on laptops other than the Framework, which tends to surface new issues.

#### Progress

Suspend-to-idle loop and hangs:

- Figured out the cause of the GPE processing hangs (e.g. on AC plug/unplug events while suspended). AML executed during GPE processing calls `AcpiOsSleep()`, which uses `pause()`, which locks up once the clock is suspended. Fixed in [PR #72 - acpi: Use DELAY() when sleeping while clock suspended](https://ron-dev.freebsd.org/FreeBSD/src/pulls/72).
- Opened [D60649 - acpi_cpu: Make disabling idle during suspend sysctl](https://reviews.freebsd.org/D60649), since superseded by [PR #71 - acpi_cpu: No longer disable idle during suspend](https://ron-dev.freebsd.org/FreeBSD/src/pulls/71). Disabling idle during suspend is incompatible with suspend-to-idle, which needs CPUs to be in their idle states.
- Figured out why certain Wayland clients such as Kitty hang, and prototyped fixes both on the FreeBSD side and the Kitty side.
- Reviewed ACPI changes:
  - [D60131 - acpi_ec: Re-arm EC event reporting after resume](https://reviews.freebsd.org/D60131).
  - [D60655 - acpica: Add a thread safe acpi_get_name](https://reviews.freebsd.org/D60655).
  - [D60373 - acpi: Tasks: Ensure sane values for number of tasks and threads](https://reviews.freebsd.org/D60373).
  - [D60374 - acpi: Tasks: Size the number of tasks with the actual number of CPUs](https://reviews.freebsd.org/D60374).
  - [D60379 - acpi: Tasks: Use M_WAITOK to allocate the taskqueue](https://reviews.freebsd.org/D60379).

Device suspend for S0i3:

- Committed `02880ddf9ed0` from [D49453 - thunderbolt: Router suspend routine](https://reviews.freebsd.org/D49453).
- Committed `16d92e92ca12` from [D51589 - amdgpio: Suspend routine](https://reviews.freebsd.org/D51589).
- Opened [D60540 - thunderbolt: NHI resume routine](https://reviews.freebsd.org/D60540). This is a stopgap to enable re-suspending of USB4 controllers. Without this, your system will only enter S0i3 once before needing to reload the `tb` kernel module.
- Committed `cd96657b6708` ("amdsmu: Print how long system spent in S0i3") and `cb77c4e846d4` ("amdsmu: Don't rely on s0i3_last_entry_status metric").
- Opened [PR #70 - amdsmu: Use devclass name instead of module name](https://ron-dev.freebsd.org/FreeBSD/src/pulls/70), fixing the hints about which kernel modules to load when an IP block is blocking S0i3 entry.
