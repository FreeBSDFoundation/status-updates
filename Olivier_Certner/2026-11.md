- ULE: Fix currently rare deadlock on stealing a blocked migrated thread
  - First analysis prompted by the "ULE: run queue lock deadlock in
    sched_switch_migrate() + tdq_move()" mails (initial report by `avg@`).
    Proposed patch does look too pessimal for cores trying to steal remote
    threads, as it aborts stealing on a lock-blocked thread.  Request that it is
    put up to review so that we can improve it.
  - Create [D61448](https://reviews.freebsd.org/D61448) ("sched_ule: Fix rare
    deadlock on stealing a blocked migrated thread") with a first approach where
    a core will not consider a blocked thread for stealing, but will continue
    with other candidates.
  - `avg@` points out that D61448 leads to removing a barrier, and asks whether
    this is fine.  After a longer analysis, code probably works without the
    barrier but for better guarantees and intelligibility, restoring would be
    better.
  - Completely change strategy (rendering the previous point obsolete), so that
    even a lock-blocked thread can still be migrated.  This is important to
    ensure we will not get into a pathological situation where a CPU stays idle
    because it cannot steal a just switched-out thread and there is no other
    thread to steal (the target CPU has two threads, with one running).  To this
    end, ensure that `sched_switch_migrate()` only pushes a thread to another
    CPU's queue while also holding the lock for its own queue, so that there can
    be no deadlock with it needing to re-acquire its own lock before
    lock-unblocking the thread.  Update
    [D61448](https://reviews.freebsd.org/D61448) ("sched_ule: Fix rare deadlock
    on stealing a blocked migrated thread") accordingly.
  - Rework the description of the problem and the commit message.
  - Commit side small changes:
